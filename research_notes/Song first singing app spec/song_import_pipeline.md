# Song import pipeline: audio file to singing-practice material (Apple Silicon, late 2026)

Research date: 2026-11-13. Target: personal single-user React web app, Apple Silicon MacBook Pro, user-supplied audio.

## 1. Vocal/instrumental source separation

### Takeaway
Use the `audio-separator` Python package (MIT, v0.48.0, released 29 Oct 2026) with a BS-RoFormer vocal model as the default separator; it is actively maintained, runs on MPS/CoreML, and its listed BS-RoFormer model scores about 2 dB higher vocal SDR than `htdemucs_ft`. Demucs itself is archived (still usable, and extremely fast via the `demucs-mlx` port), and in-browser separation works but costs a 170+ MB model download, cross-origin-isolation headers and lower/unknown speed, so it is not worth it for a Mac-only app with a local import step.

### Cited Findings

Tools and maintenance

- Install on Apple Silicon: `pip install "audio-separator[cpu]"` (the `[cpu]` extra is the one for Apple Silicon; `[gpu]` is CUDA). PyTorch models use MPS; ONNX (MDX) models use CoreML when available. - CLI usage: `audio-separator /path/to/audio.wav --model_filename model_bs_roformer_ep_317_sdr_12.9755.ckpt`; list models with `audio-separator --list_models`; top vocal models with `audio-separator -l --list_filter=vocals --list_limit=5`; ensembles with `audio-separator audio.wav --ensemble_preset vocal_balanced`. - The original Demucs repo (`facebookresearch/demucs`) was archived on 1 Jan 2025 and is read-only; the README says it "is not maintained anymore" and points to `adefossez/demucs`, where only important bug fixes are handled. - `mlx-audio-separator` (MIT, author ssmall256, v0.1.20 released 2 Oct 2026, PyPI classifier "3 - Alpha") is an MLX port of audio-separator's inference paths (Roformer, MDXC, MDX, VR, Demucs) with no PyTorch/ONNX Runtime at inference. ### Inferences
- Recommended separator: `audio-separator` 0.48.0 + `model_bs_roformer_ep_317_sdr_12.9755.ckpt` (vocals + instrumental in one pass). It is the maintained "hub" package (it also loads Demucs, MDX and Mel-Band RoFormer), so swapping models later is a one-flag change. Suggested command (uv form of the documented pip command): `uv tool install "audio-separator[cpu]"` then `audio-separator song.flac --model_filename model_bs_roformer_ep_317_sdr_12.9755.ckpt --output_format FLAC --output_dir <pkg>`.
- Speed option: `mlx-audio-separator` runs the same checkpoint about 2x faster but is alpha and validated on one machine; treat as an optional accelerator behind a flag, not the default.
- Fast fallback: `demucs-mlx` `htdemucs`/`htdemucs_ft` separates a song in seconds. Quality is about 2 dB lower vocal SDR than BS-RoFormer on the audio-separator listing, which typically shows up as more instrumental bleed in the vocal stem (hurts pitch tracking) and more vocal residue in the instrumental. Demucs's 4-stem output is useful for a different reason: see section 5 (keep drums un-pitch-shifted).
- The SDR figures in audio-separator's list are probably MVSEP "Multisong"-style scores copied from model filenames/metadata; the page fetch did not say which dataset. Treat them as relative rankings only.
- The best MVSEP leaderboard entries (14+ dB) are MVSEP-hosted models/ensembles; I did not verify whether their weights are downloadable. The practical open-weights ceiling in `audio-separator` is the ~12.9 dB BS-RoFormer family.
- Backing vocals: a lead-vs-backing ("karaoke") model pass on the vocal stem before pitch tracking should reduce harmony-induced pitch errors. `audio-separator` has a `karaoke` ensemble preset (3 models); that its purpose is lead/backing separation is inferred from the name and UVR convention (background, unverified).
- In-browser separation is technically practical in Chrome with WebGPU but strictly worse for this user: bigger setup (172 MB+ model fetch, COOP/COEP headers that also constrain the rest of the app), HTDemucs-level quality unless using NC-licensed RoFormer ONNX, no published runtimes, and memory pressure. A local CLI is both better quality and less risk.
- Licence posture: all recommended separation code is MIT; model weights vary (RoFormer community weights are often CC-BY-NC-SA). Because models run locally as part of a separate CLI and nothing is bundled into or distributed with the web app, this is acceptable for personal non-commercial use.

### Gaps
- No absolute runtime found for BS-RoFormer on Apple Silicon for a 4-minute song (only relative speed-ups). Measure at spec time with `mlx-audio-separator --benchmark` and `time audio-separator ...`. Since import is one-time, even a few minutes is acceptable.
- Licence of the specific `model_bs_roformer_ep_317` (viperx) weights was not verified.
- `free-music-demixer` did not surface in searches; its current status is unknown.
- Ultimate Vocal Remover (GUI) status was not checked; `audio-separator` covers the same model zoo from the CLI.

## 2. Vocal melody to timed notes

### Takeaway
There is no turnkey tool that yields clean singing-target notes without review; the most reliable design is: isolated lead vocal → frame-level f0 (SwiftF0, as UltraSinger now uses) → note segmentation constrained by forced-aligned word/syllable boundaries, with a dedicated note-transcription model (openvpi GAME, successor of SOME) as the alternative segmenter, followed by a small piano-roll correction UI. UltraSinger (MIT) implements almost exactly this pipeline end to end and emits UltraStar txt + MIDI, but is CPU-only on macOS, self-described as "still under development", and publishes no accuracy numbers.

### Cited Findings

UltraSinger
- UltraSinger creates UltraStar.txt, MIDI and note files from audio; can also re-pitch existing UltraStar files and add timing/text/pitch to them; computes a possible in-game score. Licence MIT. 563 stars, 602 commits, 43 open issues. — [rakuri255/UltraSinger](https://github.com/rakuri255/UltraSinger)
- Pipeline: Demucs separation (default `htdemucs`; also `htdemucs_ft`, `htdemucs_6s`, `hdemucs_mmi`, `mdx*`; can be disabled) → Whisper transcription (default `large-v2`, options up to `large-v3`; `--whisper_align_model`, `--whisper_batch_size`, `--whisper_compute_type` int8 on CPU) → SwiftF0 pitch detection (described as faster and more accurate than CREPE; detects 46.875 Hz (G1) to 2093.75 Hz (C7); the README also says UltraSinger "uses 60 Hz and 400 Hz" without explanation) → hyphenation (on by default; splits words without checking that the split matches the sung audio) → key quantization (on by default; snaps notes to the detected key, removing slides and out-of-key notes) → UltraStar txt (format 1.2.0 default; 0.3.0/1.0.0/1.1.0 selectable), karaoke txt, MIDI, optional sheet music via MuseScore, optional plots (`--plot`) and audio chunks. — [rakuri255/UltraSinger](https://github.com/rakuri255/UltraSinger)
- Install: Python 3.12, ffmpeg on PATH, OS install script from `install/`, launch with `run_on_mac.command`; README states there is no CUDA on macOS so processing is CPU-only there. CLI: `UltraSinger.py -i <audio|UltraStar.txt> -o <outdir>` plus options such as `--whisper`, `--language`, `--demucs`, `--disable_separation`, `--disable_hyphenation`, `--quantize_to_key`, `--keep_cache`, `--format_version`, `--interactive`, `--force_cpu`. README warns "Not all options working now!" and advises use only on Creative Commons songs. — [rakuri255/UltraSinger](https://github.com/rakuri255/UltraSinger)
- Latest release notes entry: 0.0.13dev16 (2026-03-04): "Drop crepe for SwiftF0", key quantization added, scale detection optimised, upgrade to Python 3.12 with a uv-based installer, interactive mode, video input. 0.0.12 (2024-12-19): words are split at note changes; UltraStar format 1.2.0. — [UltraSinger ReleaseNotes.md](https://raw.githubusercontent.com/rakuri255/UltraSinger/main/ReleaseNotes.md)
- UltraSinger README gives no accuracy metrics. Its two score modes: "simple" (pitch class only, like the game) and "accurate" (exact octave). — [rakuri255/UltraSinger](https://github.com/rakuri255/UltraSinger)
- A fork PR (MrDix/UltraSinger #55) uses LRCLIB synced lyrics plus wav2vec2 CTC forced alignment via WhisperX for word timing and claims lyric coverage of about 100% vs about 50% and better timing; this is the PR author's claim (search-result summary; page not opened). — [MrDix/UltraSinger PR 55](https://github.com/MrDix/UltraSinger/pull/55)

Dedicated singing-transcription models
- GAME ("Generative Adaptive MIDI Extractor", openvpi) is "the upgraded successor of SOME", for transcribing singing voice into scores. Code MIT. Claims it "works on dirty or separated voice mixed with noise, reverb or even accompaniments"; outputs floating-point pitch values; boundary and note-presence thresholds are adjustable; uses D3PM diffusion to trade quality vs speed; multilingual with a language hint to improve segmentation. Inference: `python infer.py extract <path> -m <model> --output-formats mid,txt,csv`. Tested with Python 3.12, PyTorch 2.8.0, Lightning 2.6.1 (CUDA); `deploy.py` exports ONNX (opset 17). No accuracy figures on the README; no macOS/MPS notes. 301 stars, 206 commits, 1 open issue. — [openvpi/GAME](https://github.com/openvpi/GAME)
- A community Hugging Face mirror references GAME release v1.0.3 and says the model files are CC BY-NC-SA 4.0 (search-result summary; mirror page not opened). — [aaatmy/game-large-onnx](https://huggingface.co/aaatmy/game-large-onnx)
- SOME (openvpi, MIT) is the older predecessor and describes itself as beta with no backward-compatibility guarantee (search-result summary). — [openvpi/SOME](https://github.com/openvpi/SOME)
- ROSVOT (2024) claims state-of-the-art singing transcription on clean or noisy input, and a 2026 SoulX-Singer paper uses ROSVOT for pitch-class estimation and note-boundary detection in its data pipeline (search-result summary of abstracts). — [ROSVOT arXiv 2405.09940](https://arxiv.org/pdf/2405.09940), [arXiv 2602.07803](https://arxiv.org/html/2602.07803v2)
- VocalParse (2026, arXiv 2605.04613) is a unified singing-transcription model built on a large audio-language model that outputs interleaved lyric, pitch and note tokens with a global BPM; model card reports CER/pitch MAE/note MAE without comparison to other systems (search-result summary). — [Hugging Face ngoctham/VocalParse](https://huggingface.co/ngoctham/VocalParse)

Spotify basic-pitch
- basic-pitch is Apache-2.0, polyphonic and "instrument-agnostic", works best on one instrument at a time; outputs MIDI with pitch bends, optional note-event CSV (`--save-note-events`) and raw model output NPZ; install `pip install basic-pitch`; README lists Python 3.7–3.11 and limits Apple Silicon to Python 3.10 with CoreML as the default macOS backend; repo not archived but shows no releases, 49 open issues and 17 open PRs; README makes no claim about vocals. — [spotify/basic-pitch](https://github.com/spotify/basic-pitch)

Real-world reference
- The Nightingale karaoke app notes that its pitch scoring is "less accurate when stem separation is skipped and scoring uses the original mix". — [Nightingale docs: lyrics](https://nightingale-379.pages.dev/docs/lyrics)

### Inferences
- Recommended approach (build in the import CLI, borrowing UltraSinger's design):
  1. Input = lead-vocal stem (optionally after a backing-vocal removal pass), mono, 16 kHz for the tracker.
  2. Frame-level f0 with SwiftF0 (already chosen for the mic side by earlier research, so target and live pitch share one tracker and its biases); keep voicing confidence. Save the raw f0 curve in the package for display behind the notes.
  3. Segment notes inside each forced-aligned word (section 3): take the confidence-weighted median pitch over the voiced frames of the word; split the word into multiple notes when the smoothed pitch moves by more than about 0.7–1 semitone and stays there for at least about 100–120 ms (this is how melisma becomes "~" continuation notes in UltraStar terms).
  4. Round to integer MIDI for the target but also store the fractional median (cents) so the UI can show where the original singer actually sat.
- Clean-up heuristics that address the common errors (background knowledge of standard practice; thresholds are starting points to tune):
  - Vibrato split into notes: median-filter f0 over about 50–80 ms, apply hysteresis (a new note needs a sustained change of more than about 0.7 semitone for more than 100 ms), then merge adjacent notes with equal rounded pitch and gaps under about 60–80 ms.
  - Over-segmentation: enforce a minimum note length (about 80–120 ms); absorb shorter fragments into the longer neighbour; treat fast slides/scoops at note onsets as part of the destination note.
  - Octave errors: build a duration-weighted pitch histogram per song; flag notes more than 9–12 semitones from the running median of their neighbours and test ±12; clamp the tracker's search range to a plausible band for the singer of the recording.
  - Backing vocals/harmonies: run a lead/backing separation pass first; drop note candidates with low voicing confidence or which overlap in time with a stronger note.
  - Unvoiced consonants/breaths: require voicing confidence above threshold for a minimum fraction of the word window; otherwise extend the neighbouring pitch.
  - Do not use key quantization (UltraSinger's default) as ground truth for a practice target without review: it deletes blue notes and deliberate out-of-key passing tones.
- Editing UI needed (small): a piano roll drawn over the raw f0 curve and vocal-stem waveform, with per-note drag (pitch/time), split, merge, delete, ±12 semitone, "snap to f0 median", lyric-syllable edit, and audition (synth tone + vocal stem solo, loop a phrase). Expect to touch a minority of notes per song but in every song; with only a handful of songs, 15–30 minutes of manual correction per song is a reasonable planning assumption (my estimate, not a measured figure).
- GAME is the most promising dedicated segmenter (2026, MIT code, explicitly robust to separated vocals), but: weights appear to be CC BY-NC-SA (fine for local personal use), it is CUDA-tested only, and it has no pip package. Treat it as an experiment to compare against the f0+word-boundary method on the user's actual songs, not as the baseline. ROSVOT/VocalParse are research code with heavier setup; not recommended as a first choice.
- basic-pitch is the wrong tool for a monophonic lead vocal target: it is polyphonic/instrument-agnostic, tends to emit overlapping and fragmented notes on voice, and its Apple Silicon support is pinned to old Python (background on voice behaviour is unverified; the Python pin is from the README).
- UltraSinger caveat for deep or high voices: the README's unexplained "60 Hz and 400 Hz" remark may indicate a restricted pitch window (400 Hz is about G4), which would clip melodies sung above G4 in the original key. Check the source before relying on it.
- RMVPE, CREPE and pYIN were not re-researched this session. Background (unverified): RMVPE is widely used for vocal f0 in the presence of accompaniment bleed and is a reasonable second tracker to cross-check SwiftF0; CREPE was dropped by UltraSinger in favour of SwiftF0; pYIN (in librosa) is a dependable no-ML baseline with built-in voicing probability.

### Gaps
- No quantitative note-level accuracy (onset/offset/pitch F-measure) was found for UltraSinger, GAME or the f0+segmentation approach on separated commercial vocals. Needs an empirical test on 2–3 of the user's songs.
- UltraSinger runtime on Apple Silicon CPU was not found.
- MusicYOLO and VOCANO status were not checked (a VOCANO repo exists at github.com/B05901022/VOCANO; maintenance unknown).
- GAME release date, model-weight licence (only seen via an unofficial mirror) and behaviour on MPS are unverified.

## 3. Lyrics and timing

### Takeaway
Get the text from a trusted source first (LRCLIB or user-pasted lyrics) and use ML only for timing: LRCLIB gives line-level LRC for free without a key (and now flags word-level sync where available), and a wav2vec2 forced aligner (WhisperX's) run on the separated vocal stem turns known lyrics into word timings. Pure transcription of sung vocals is still roughly 20–25% WER locally even with Whisper large-v3 on a separated stem, so it should be the last resort.

### Cited Findings

LRCLIB
- Base URL `https://lrclib.net`, CORS-enabled. `GET /api/get` requires `track_name` and `artist_name`; optional `album_name` and `duration` (1–3600 s); a record matches when duration differs by at most ±2 s and supplying duration is described as "crucial". `GET /api/get/{id}`; `GET /api/search` (`q` or `track_name`, optional `artist_name`/`album_name`, up to 20 results, no pagination); beta `GET /api/v2/search`; `POST /api/publish` needs a proof-of-work `X-Publish-Token`. — [LRCLIB docs](https://lrclib.net/docs.md)
- Response fields: `id`, `trackName`, `artistName`, `albumName`, `duration`, `instrumental`, `plainLyrics`, `syncedLyrics` (line-level LRC), `hasWordSync` (true when `lyricsfile` contains word-level timings) and `lyricsfile` (raw "Lyricsfile" YAML with `lines[].words`); records published with only plain or LRC lyrics are never word-synced. — [LRCLIB docs](https://lrclib.net/docs.md)
- No API key required. Approximate limits: about 45 requests/min per IP without a User-Agent, about 90 with an identifying User-Agent, higher for registered apps (`Lrclib-App-Id`); honour `Retry-After` on 429; a descriptive User-Agent (or `X-User-Agent`/`Lrclib-Client` from browsers) is recommended. — [LRCLIB docs](https://lrclib.net/docs.md)
- The API docs contain no licence or terms-of-service text and do not mention database dumps. — [LRCLIB docs](https://lrclib.net/docs.md)

Forced alignment and transcription
- WhisperX: BSD-2-Clause; faster-whisper (CTranslate2) backend; install `pip install whisperx` or `uvx whisperx`; the only documented Mac route is CPU (`--compute_type int8 --device cpu`); word timestamps come from wav2vec2 phoneme-model forced alignment, with default alignment models for English, French, German, Spanish and Italian via torchaudio and others via Hugging Face; stated limitations: words containing characters outside the aligner's dictionary (numbers, symbols) get no timing, and overlapping speech is handled poorly. 25.3k stars, 179 open issues. — [m-bain/whisperX](https://github.com/m-bain/whisperX)
- Nightingale (open-source karaoke app, repo `rzru/nightingale`) uses exactly the text-first pattern: query LRCLIB first and skip transcription on a hit ("faster and often more accurate for well-known songs"); otherwise WhisperX `large-v3` on the isolated vocals; word timing from wav2vec2 forced alignment (default WhisperX Viterbi on CPU). Experimental alternatives it ships: Parakeet TDT 0.6B v3 via ONNX Runtime on CPU/MPS (25 European languages), `torchaudio.functional.forced_align` for the Viterbi step, and Qwen3-ForcedAligner-0.6B (Apache-2.0; runs on MPS; about 1.8 GB weights; falls back for audio over about 5 minutes in a single pass or unsupported languages). User-supplied plain text is aligned against the audio; `.lrc`/`.elrc` files are used directly. — [Nightingale docs: lyrics](https://nightingale-379.pages.dev/docs/lyrics)
- Local lyrics-transcription benchmark on Apple Silicon (12 Creative Commons songs from JamendoLyrics MultiLang, 3 each en/fr/de/es; M5 MacBook; mlx-whisper; self-published and LLM-authored, dated 10 June 2026): mean WER vocals→large-v3 22.1%, vocals→large-v3-turbo 22.8%, full mix→large-v3 24.3%, vocals→large-v2 32.4%, vocals→Qwen3-ASR-1.7B 27.4%; `condition_on_previous_text=True` raised WER to 50.2% and caused repetition loops on 4 of 12 songs; language auto-detect cost about 4.3 WER points; an LLM line-by-line merge of three transcripts reached 15.9%. English WER for vocals→large-v3 was 22.6%. — [lyrics-bench paper](https://lyrics-bench.onrender.com/papers/paper.html)
- Same benchmark, runtimes: large-v3-turbo about 15 s/song, large-v3 about 20–36 s/song, Demucs about 21 s/song. Separation mainly suppresses hallucinations in instrumental passages (one song fell from 92% to 44% WER). Failure modes: invented text over instrumental sections, repetition loops, systematic deletion of backing vocals and ad-libs, misheard melisma, merged/split lines. Word-timing accuracy was not measured. — [lyrics-bench paper](https://lyrics-bench.onrender.com/papers/paper.html)
- stable-ts is used by third-party wrappers as the engine for aligning audio to source-of-truth text, and `syncalong` (Whisper-based) keeps lyric order fixed so repeated choruses do not collapse onto one audio segment and tolerates mishearings by fuzzy matching (search-result summaries; pages not opened). — [force-align-wordstamps](https://replicate.com/cureau/force-align-wordstamps), [syncalong: how it works](https://syncalong.readthedocs.io/en/latest/how-it-works/)
- A community fork `kalebjs/whispermlx` replaces WhisperX's inference backend with mlx-whisper for Apple Silicon (search-result summary; page not opened). — [kalebjs/whispermlx](https://github.com/kalebjs/whispermlx)

### Inferences
- Recommended lyric flow in the import CLI:
  1. Text: `GET https://lrclib.net/api/get?artist_name=..&track_name=..&duration=<secs>` with a descriptive User-Agent. If `hasWordSync`, parse `lyricsfile` words; else take `syncedLyrics` lines; else `plainLyrics`. Always allow `--lyrics path.txt|.lrc` to override (user-pasted lyrics are the most reliable text source for well-known commercial songs).
  2. Timing: forced-align the known text against the vocal stem with wav2vec2 (WhisperX `align` in Python on CPU is fine for a 4-minute song). Use LRCLIB line timestamps as anchors: align each line only within its own window (line start minus about 1 s to next line start plus about 1 s). This prevents chorus repetition from derailing global alignment and bounds any error to one line.
  3. No text available: mlx-whisper `large-v3` on the vocal stem with `condition_on_previous_text=False` and explicit `language`, then show the transcript for correction before alignment.
- Sanity check LRCLIB against the user's file: a different master/edit can shift all timestamps. Estimate a global offset by cross-correlating LRC line onsets with vocal-stem energy onsets, and surface the offset in the UI as an adjustable "lyrics offset".
- Word- vs syllable-level: wav2vec2 alignment yields word (and character) timings; on sung vowels held for seconds, word end times are unreliable because the aligner does not model sustained phonemes well (background, unverified). For practice purposes use alignment for word onsets and let the f0 voicing (section 2) decide where each note actually ends.
- Attaching lyrics to notes: one word maps to one or more notes; split the word text across notes with a hyphenation library (as UltraSinger does) only when the word has at least as many syllables as notes; otherwise put the whole word on the first note and mark later notes as continuations ("~" in UltraStar convention). Store both views: `lines[].words[]` with times, and `notes[].wordIndex`/`notes[].text`.
- Avoid depending on WhisperX GPU on Mac: its transcription backend (CTranslate2) is CPU-only on macOS per its README. Use mlx-whisper for transcription and WhisperX's alignment module (or torchaudio forced_align) for timing.

## 4. Formats: UltraStar txt, MIDI, MusicXML

### Takeaway
Use an app-specific JSON (times in seconds, MIDI pitch, lyric text per note) as the canonical in-package format, and support UltraStar txt as the import/export interchange format because it is the only widely used format that carries pitch, timing and syllables together and is what UltraSinger and community editors produce. No maintained JavaScript/TypeScript UltraStar parser was found, but the format is simple enough to parse in well under 150 lines.

### Cited Findings
- UltraStar format spec version on usdx.eu: 1.1.0 (page dated 21 Nov 2023). Files are UTF-8 without BOM. Mandatory headers `#VERSION`, `#TITLE`, `#ARTIST`; audio via `#AUDIO` (successor of deprecated `#MP3`); new `#VOCALS` and `#INSTRUMENTAL` headers for separate acapella and instrumental files; `#BPM` ("UltraStar BPM is ideally four times the song's real BPM"); `#GAP` = delay before the lyrics start in milliseconds; also `#VIDEO`, `#VIDEOGAP`, `#COVER`, `#BACKGROUND`, `#START`, `#END` (ms), `#PREVIEWSTART` (s), `#MEDLEYSTARTBEAT/#MEDLEYENDBEAT`, `#P1/#P2`, `#GENRE`, `#LANGUAGE`, `#YEAR`, `#CREATOR`, `#PROVIDEDBY`, `#COMMENT`. Deprecated: `#RELATIVE`, `#RESOLUTION`, `#NOTESGAP`, `#ENCODING`, `#DUETSINGERP1/P2`. — [UltraStar format spec](https://usdx.eu/format/)
- Note line syntax: `NoteType StartBeat Length Pitch Text`, e.g. `: 0 1 8 Normal`. Types: `:` normal, `*` golden (double points), `F` freestyle (not scored), `R` rap, `G` rap golden. Pitch 0 corresponds to C4 (MIDI 60). `- StartBeat` marks a phrase/line break; `E` ends the file; `P1`/`P2` lines switch duet singer. — [UltraStar format spec](https://usdx.eu/format/)
- The spec page as fetched contains internal inconsistencies (units/examples for `#START`, `#VIDEOGAP`, `#PREVIEWSTART`) and does not give the beat-to-millisecond formula or the rules for spaces and `~` in syllable text. — [UltraStar format spec](https://usdx.eu/format/)
- UltraSinger writes format 1.2.0 by default (also 0.3.0/1.0.0/1.1.0) and describes 2.0.0 as upcoming. — [rakuri255/UltraSinger](https://github.com/rakuri255/UltraSinger)
- Parsers found: JavaScript `syllabesjs` (TypeScript, parses UltraStar among other lyric formats, last pushed 2016); Python `ultrastarParser` (PyPI, 0.6.x series); Go `codello.dev/ultrastar/txt`. No maintained npm UltraStar parser surfaced. — [komanaki/syllabesjs](https://www.github.com/komanaki/syllabesjs), [PyPI ultrastarParser](https://pypi.org/project/ultrastarParser/0.6.9), [codello.dev/ultrastar/txt](https://pkg.go.dev/codello.dev/ultrastar/txt)
- Copyright context: the UltraStar Play FAQ says the project ships no audio, video or lyrics and that there is no official song service or sharing platform "due to copyright issues"; the spec notes many third parties host txt files of varying quality (hence `#PROVIDEDBY`); Performous only repackages songs whose packages carry licence files. — [UltraStar Play FAQ](https://github-users.yhajoa.workers.dev/UltraStar-Deluxe/Play/wiki/Frequently-Asked-Questions-(FAQ)), [UltraStar format spec](https://usdx.eu/format/), [Performous songs](https://performous.org/songs)
- A German (Munich regional court) ruling treats song lyrics as protected works of language (search-result summary of a law-firm article about AI chatbots; indirectly relevant). — [MTR Legal](https://www.mtrlegal.com/en/ai-chatbot-must-not-use-copyrighted-song-lyrics/index.md)

### Inferences
- Conversion formulas (background knowledge of the USDX convention, not stated on the spec page; verify against the USDX source or the Python/Go parsers before coding): `time_ms(beat) = GAP + beat * 60000 / (BPM * 4)`; `midi = 60 + Pitch`. Because the file BPM is a free resolution parameter, a generated file can use any BPM that makes one beat about 15–40 ms. Comma decimal separators (`#BPM:120,5`) occur in the wild and must be accepted.
- Syllable text conventions (background, unverified): a leading or trailing space in the note text marks a word boundary; `~` is a continuation of the previous syllable on a new pitch. A parser must preserve the whitespace in the text field rather than trim it.
- Octaves in community files are unreliable: the games score by pitch class, so charters frequently place notes an octave away from the real sung pitch (UltraSinger's "simple" vs "accurate" scores reflect this). After importing a community file, re-anchor octaves against the f0 of the vocal stem (choose the octave shift per phrase that minimises distance to the measured f0 median).
- Community txt files also assume a specific audio version: `#GAP` will usually need re-fitting to the user's own file (same offset estimation as for LRCLIB in section 3).
- MIDI alternative: fine as an export (notes plus lyric meta-events) and easy to inspect in a DAW, but tempo-map/tick indirection and weak lyric conventions make it a poor canonical format. MusicXML is notation-oriented (requires rhythmic quantisation and measure structure) and is overkill for a continuous-time practice target. JS libraries for these (for example `@tonejs/midi`, OpenSheetMusicDisplay) were not checked this session (background, unverified).
- Recommended canonical schema (design proposal): `notes: [{ t: seconds, d: seconds, midi: int, cents: float, text: string, word: int, line: int, kind: "normal"|"freestyle" }]`, `lines: [{ t0, t1, text, words: [{ t0, t1, text }] }]`, plus `transpose` applied at playback time rather than baked in. Write a tiny in-house `ultrastar.ts` (parse + serialise) with tests; do not depend on the 2016 `syllabesjs`.
- Copyright considerations for a personal tool: a community UltraStar file embeds the full lyric text (a protected work) and a transcription of the melody, generally shared without a licence from rights holders. Loading a file the user found into a private, local, non-distributing app is low-risk in practice, but the app should not bundle, fetch on the user's behalf from song databases, re-host or share such files, and song packages should stay out of any public repo. This is not legal advice; no authoritative statement on USDB-style sites' legal status was found.

### Gaps
- The 1.2.0 / 2.0.0 UltraStar spec text was not retrieved (usdx.eu served 1.1.0); differences that matter for a parser are unknown.
- No authoritative legal source on community UltraStar charts (note data plus lyrics) was found.
- Maintained JS/TS parsers for MIDI/MusicXML were not verified this session.

## 5. Key change and tempo change of the instrumental

### Takeaway
Use Signalsmith Stretch (MIT, official WASM/AudioWorklet build on npm as `signalsmith-stretch`) for live key and tempo control in the browser: it is the only high-quality option whose licence allows bundling, and its API (load buffers, schedule rate + semitones) fits a practice player directly. Use the Rubber Band CLI with the R3 "fine" engine (GPL, invoked as a separate program) to optionally pre-render the chosen key at import time for best quality; SoundTouchJS (now MPL-2.0) is the lower-quality fallback.

### Cited Findings

Signalsmith Stretch
- MIT licence. Official Web Audio release lives in the repo's `web/` folder (WASM/AudioWorklet) and is published on npm as `signalsmith-stretch`; the stretching algorithm is kept in sync with the C++ library. Repo: 580 stars, 116 commits, 11 open issues. — [Signalsmith-Audio/signalsmith-stretch](https://github.com/Signalsmith-Audio/signalsmith-stretch)
- Quality claims: handles large pitch shifts across multiple octaves; time-stretching "sounds best for modest changes", roughly 0.75x to 1.5x. A "tonality limit" uses a non-linear frequency map to preserve more timbre. Formant correction exists (`setFormantFactor`, `setFormantBase`, compensate-pitch flag) but is described as less sharp than monophonic methods such as PSOLA. Presets `presetDefault` and `presetCheaper`. `splitComputation` spreads the periodic heavy spectral computation more evenly at the cost of one extra interval of latency, for strict real-time contexts. — [Signalsmith-Audio/signalsmith-stretch](https://github.com/Signalsmith-Audio/signalsmith-stretch)
- Web API: `SignalsmithStretch(audioContext, ?channelOptions)` returns a Promise resolving to an `AudioNode` with extra methods; UMD `.js` and ES module `.mjs` builds. Two modes: live input, or loaded buffers. Methods: `addBuffers([...channels])` (typed arrays per channel; returns Promise of end time), `dropBuffers(?toSeconds)`, `schedule({ output, active, input, rate, semitones, tonalityHz (default 8000), formantSemitones, formantCompensation, formantBaseHz (about 100 low voice / 400 high voice, 0 to pitch-track), loopStart, loopEnd })`, `start(?when)`, `stop(?when)`, `latency()`, `inputTime` plus `setUpdateInterval(seconds, ?callback)`, and `configure({ blockMs, intervalMs, splitComputation, preset: "default"|"cheaper" })`. Changes should be scheduled ahead by at least `latency()` for clean transitions. — [signalsmith-stretch web README (unpkg)](https://unpkg.com/signalsmith-stretch/README.md)

Rubber Band
- Rubber Band Library v4.0.0 was released 25 Oct 2024 (new simplified pitch-shifting API). Licence: GPL, with a commercial licence for proprietary distribution. A free command-line utility is provided, with a macOS executable for v4.0.0. — [Rubber Band Library](https://breakfastquay.com/rubberband/)
- CLI: `rubberband [options] in.wav out.wav`; `-t<X>` stretch to X times duration, `-T<X>` tempo multiple, `-p<X>` pitch in semitones, `-f<X>` frequency ratio; `-2`/`--fast` selects the R2 engine (default), `-3`/`--fine` selects R3, which "almost always produces better results" with "significantly higher CPU load"; `-F`/`--formant` preserves the formant envelope; `--centre-focus` preserves centre-panned material; `-c<N>` crispness applies to R2 only; `--pitch-hq`; `--realtime`; `--ignore-clipping`. Example for 80% tempo and 4 semitones down: `rubberband -T 0.8 --pitch -4 input.wav output.wav` (add `-3` for R3). — [Rubber Band CLI usage](https://breakfastquay.com/rubberband/usage.txt)
- WASM builds exist but are GPL and third-party: `rubberband-web` (delude88; ready-made AudioWorklet and WebWorker, `createRubberBandNode`; a third-party listing shows it last updated about 2 years ago), `Daninet/rubberband-wasm` (listed GPLv2), `@echogarden/rubberband-wasm` 0.2.0, `@slangeder/rubberband-wasm` 2.0.2 (search-result summaries; pages not opened). — [rubberband-web](https://classic.yarnpkg.com/en/package/rubberband-web), [Daninet/rubberband-wasm](https://www.github.com/Daninet/rubberband-wasm), [@echogarden/rubberband-wasm](https://cdn.jsdelivr.net/npm/@echogarden/rubberband-wasm@0.2.0/README.md)

SoundTouchJS
- `@soundtouchjs/audio-worklet` (README of 2.0.3) is an AudioWorklet implementation; the project "moved from LGPL to MPL-2.0". `SoundTouchNode` extends `AudioWorkletNode` with AudioParams `pitch` (0.1–8), `pitchSemitones` (−24 to 24) and `playbackRate`. There is no tempo parameter: tempo is set on the source node (`source.playbackRate`) and mirrored on the node, which then compensates pitch; for `<audio>` elements set `preservesPitch = false`. Values far from 1.0 "tend to produce more artifacts"; an underrun `metrics` counter is exposed; an offline `processOffline()` is exported. — [@soundtouchjs/audio-worklet README](https://cdn.jsdelivr.net/npm/@soundtouchjs/audio-worklet@2.0.3/README.md)
- `bungee-pitch-shift` (npm) is another WASM pitch-shift/time-stretch option for Web Audio (search-result summary; page not opened). — [bungee-pitch-shift](https://www.pkgstats.com/pkg:bungee-pitch-shift)

### Inferences
- Quality expectation for a full instrumental mix, −1 to −6 semitones and 70–85% speed: phase-vocoder-family stretchers (Signalsmith, Rubber Band R3) keep harmonic content clean but soften drum transients and can sound slightly "phasey"; downward shifts additionally darken cymbals and make kick/bass heavier. Signalsmith's own stated sweet spot ends at 0.75x, so 70% speed is just outside it and 75–85% is inside. SoundTouch (time-domain WSOLA-style) tends to produce audible flutter/doubling on polyphonic mixes at these settings (SoundTouch behaviour is background, unverified). No measured listening comparison for this exact use was found.
- High-value trick: drums are unpitched, so do not pitch-shift them. Separate drums (a 4-stem Demucs pass on the instrumental, seconds with `demucs-mlx`), pitch-shift only the bass+other stem, and mix drums back unshifted (time-stretch still applies to both). This removes the most objectionable artefact of large downward shifts. It doubles the stems the player must keep in sync, so do it as a pre-render at import time rather than live.
- Live vs pre-render recommendation:
  - Live (Signalsmith in an AudioWorklet): required anyway for tempo changes and A/B looping, and lets the user audition keys instantly. One stereo stream at default preset is a small load on Apple Silicon (no benchmark figures were found; `preset: "cheaper"` and `splitComputation` exist if glitches occur).
  - Pre-render (Rubber Band R3 offline via CLI, optionally with the drums trick): once the key for a song is settled (a per-song, one-time decision for this user), bake `instrumental_k-4.flac` etc. Then live processing only handles tempo, and at 100% tempo the stretcher can be bypassed entirely for artefact-free playback.
  - Suggested design: the package always contains the original-key instrumental; the CLI has `songprep render-key <song> --semitones -4` to add a baked variant; the player uses a baked variant when one matches the selected key and otherwise shifts live.
- Guide vocal: when the vocal stem is played as a guide in the shifted key, shift it with formant preservation (Rubber Band `--formant`, or Signalsmith `formantCompensation: true` with `formantBaseHz` near the singer's range) to avoid the "slowed-down tape" timbre. Target notes simply get `midi + semitones`; an option to drop the target a further octave (−12) is useful for a deep voice singing high-tenor or female leads.
- Browser-native `playbackRate` with `preservesPitch` gives tempo change only (no key change) on media elements, with speech-oriented quality; acceptable as a zero-dependency fallback for tempo when using pre-rendered key variants, but media elements are harder to keep sample-synchronised across multiple stems than AudioWorklet playback (background, unverified).
- ffmpeg alternative for pre-rendering: the `rubberband` audio filter (requires an ffmpeg build with librubberband), e.g. pitch ratio 2^(−4/12) = 0.7937 for −4 semitones. Filter option names and Homebrew build flags were not verified this session; the standalone `rubberband` CLI above is verified. `brew install rubberband` is the expected install route (background, unverified).
- Licensing: Signalsmith (MIT) and SoundTouchJS (MPL-2.0) can be bundled in the web app; Rubber Band and its WASM ports are GPL, so keep Rubber Band strictly as a separately invoked CLI and do not bundle a Rubber Band WASM build.

- No objective or listening-test comparison of Signalsmith vs Rubber Band R3 vs SoundTouch on full mixes at −1 to −6 semitones / 70–85% tempo was found, and no real-time CPU measurements in an AudioWorklet.

## 6. Song analysis for practice (beats, key, phrases, range)

### Takeaway
Use `beat_this` (CPJKU, ISMIR 2024) for beat and downbeat tracking; it is reported as the current state of the art and does not need madmom's hard-to-install DBN. Derive phrases from lyric lines plus rests, and compute range/tessitura directly from the cleaned note list to recommend a transposition; these need no extra ML.

### Cited Findings
- Beat This! is the official CPJKU implementation of "Beat This! Accurate Beat Tracking Without DBN Postprocessing" (Foscarin, Schlüter, Widmer, ISMIR 2024) for beat and downbeat tracking. Install is via pip from the GitHub main-branch zip; it needs ffmpeg or another torchaudio backend; uses the first GPU by default and falls back to CPU. — [PyPI beat-this](https://pypi.org/project/beat-this/)
- madmom is optional for beat_this (only for `--dbn` post-processing) and must be installed from the CPJKU GitHub repo because the PyPI release only supports Python below 3.10 and numpy below 1.20. — [PyPI beat-this](https://pypi.org/project/beat-this/)
- A May 2026 arXiv paper evaluates Beat This against madmom's DBNBeatTracker and Beat Transformer and describes Beat This as the current state of the art (search-result summary). Reported F1 for Beat This: 97.5 on Ballroom, 62.7 on the hard SMC set (via a paper-listing site). — [arXiv 2605.12287](https://arxiv.org/html/2605.12287), [Beat This paper listing](https://vercel.hyper.ai/en/papers/2407.21658)
- Nightingale runs "a quick key-detection pass" to enable key and tempo shifts, and shows a countdown during long lyric gaps (a practice-relevant UI pattern). — [Nightingale docs: lyrics](https://nightingale-379.pages.dev/docs/lyrics)
- UltraSinger includes scale/key detection used for its key quantization (optimised in 0.0.13dev16). — [UltraSinger ReleaseNotes.md](https://raw.githubusercontent.com/rakuri255/UltraSinger/main/ReleaseNotes.md)

### Inferences
- Beats/downbeats: run `beat_this` on the full mix (or the instrumental stem) and write `beats[]` and `downbeats[]` in seconds. Uses: count-in clicks before a phrase (count back N beats from the phrase's first note, aligned to the previous downbeat), loop boundaries snapped to bars, and a metronome overlay at reduced tempo. Sanity-check for half/double-tempo errors by comparing the median inter-beat interval with a 70–180 BPM prior, and expose "halve/double tempo" in the editor. Whether beat_this runs on MPS was not verified; CPU is adequate for a one-time 4-minute analysis.
- Key detection: needed only as a label and as a hint for enharmonic spelling; a template-matching estimate on the instrumental's chroma (for example Krumhansl-style profiles in librosa or Essentia's key extractor) is sufficient (tools are background, unverified this session). A cheap cross-check is the duration-weighted pitch-class histogram of the transcribed melody itself.
- Phrases: primary boundaries are lyric lines (LRCLIB/LRC lines or UltraStar `-` breaks); split long lines and merge fragments using rests (a gap over about 0.4–0.6 s between notes, or over one beat) and snap phrase starts to the preceding beat for count-ins. Store `phrases[] = { t0, t1, firstNote, lastNote, lineIndex }`.
- Range and tessitura from the note list: `range = [min midi, max midi]` over notes longer than about 150 ms (ignore brief outliers and freestyle notes); `tessitura = duration-weighted 10th–90th percentile band` plus the duration-weighted median; also report "time above X" for the top few semitones. All trivial once notes are clean, so compute them in the web app as well so they update after manual edits.
- Key-shift recommendation: with the singer's comfortable range `[lo, hi]` and absolute limits `[minAbs, maxAbs]` stored in a profile, evaluate shifts s from −12 to +12: cost(s) = Σ over notes of duration × penalty(distance outside `[lo, hi]`) with a large penalty outside `[minAbs, maxAbs]`, plus a small |s| term to favour less processing; also evaluate each s with the target dropped an octave (singer sings an octave below the shifted instrumental), which for a deep male voice on high leads is often the real answer and needs a smaller instrumental shift. Present the top 2–3 options with "highest note / lowest note / % time in comfortable range".
- `all-in-one` (structure analysis: sections, beats, downbeats) could label verse/chorus for navigation, but it was not checked this session, has historically had heavy dependencies (madmom, Demucs), and lyric-line phrases already cover the practice need. Not recommended for v1.

- `all-in-one`, Essentia and librosa key/tempo tooling status and Apple Silicon install were not researched this session.
- No downbeat-specific accuracy numbers for beat_this on pop music were retrieved, and its MPS support is unverified.
- The current beat_this version/release date was not retrieved.

## 7. Architecture and how the web app loads songs

### Takeaway
The most robust design for a Mac-only personal app is a local Python CLI managed with `uv` that writes a self-contained "song package" folder, which the web app loads as static files; all heavy tools (PyTorch/MLX models, Rubber Band, ffmpeg) stay outside the browser and outside the app's licence surface. A local HTTP service adds a daemon without adding capability, and fully in-browser processing is lower quality and more fragile.

### Cited Findings
- The File System Access API (`showDirectoryPicker()`) is available in Chromium browsers (Chrome/Edge 86+) on macOS; Firefox and Safari do not support it; the web-platform-dx explorer lists it as "Limited availability"; handles can be serialised for reuse. Sources were not dated 2026 (search-result summaries). — [Chrome for Developers: File System Access](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access), [web.dev: open a directory](https://web.dev/patterns/files/open-a-directory), [web-features explorer](https://web-platform-dx.github.io/web-features-explorer/features/file-system-access)
- Every ML component recommended above ships as a Python package or script with a CLI (`audio-separator`, `mlx-audio-separator`, `demucs-mlx`, `whisperx`, GAME's `infer.py`, UltraSinger), and several document `uv`-based installs (`uvx whisperx`; UltraSinger's installer moved to uv). — [PyPI audio-separator](https://pypi.org/project/audio-separator/), [m-bain/whisperX](https://github.com/m-bain/whisperX), [UltraSinger ReleaseNotes.md](https://raw.githubusercontent.com/rakuri255/UltraSinger/main/ReleaseNotes.md)
- In-browser ML separation requires cross-origin isolation headers (COOP/COEP) and large model downloads (about 172 MB for HTDemucs ONNX). — [timcsy/demucs-web](https://github.com/timcsy/demucs-web)
- `audio-separator` CLI writes FLAC by default at 44.1 kHz. — [PyPI audio-separator](https://pypi.org/project/audio-separator/)
- Nightingale's design (desktop app with an analysis pipeline producing cached per-song transcripts, with LRCLIB-first lyrics and per-song overrides) is a working precedent for "analyse once, then play from cache". — [Nightingale docs: lyrics](https://nightingale-379.pages.dev/docs/lyrics)

### Inferences
- Option comparison:
  - Local CLI + package folder (recommended): simplest to build and debug, re-runnable per stage, no long-running process, tools can be GPL or NC-licensed without touching the web app. Friction is one terminal command per song, which the brief accepts.
  - Local HTTP service (for example FastAPI wrapping the same functions): only buys an "Import" button in the browser, at the cost of a daemon that must be running, CORS/port handling and progress streaming. Build later as a thin wrapper if wanted; design the CLI as a library with a `main()` so this is cheap.
  - Fully in-browser: avoid (section 1).
- How the web app reads packages, in order of preference:
  1. Static files: the CLI writes to a `songs/` directory that the app's local server exposes (Vite `public/songs/` in dev, or any static server/launchd job for a built app) plus a generated `songs/index.json`. Zero daily friction, works in any browser, supports HTTP range requests, nothing to re-grant.
  2. If the app is hosted remotely (for example on Vercel) rather than served locally: drag-and-drop the package folder once and copy it into OPFS (origin-private file system), keyed by song id; works in Chrome and Safari, survives reloads, but duplicates the data and is subject to browser storage eviction unless persistence is granted (OPFS details are background, unverified this session).
  3. File System Access API directory handle stored in IndexedDB: Chrome-only and may re-prompt for permission; only worth it if the user wants the app to write edits back to the package folder directly from the browser.
- Writing edits back: note/lyric corrections made in the browser must persist. With option 1, simplest is "Export corrected notes.json" (download) or a tiny dev-server middleware endpoint that writes `notes.json`; with option 3 the app can write in place. Keep the CLI's raw output (`notes.auto.json`) separate from the user-edited file (`notes.json`) so re-running import never destroys manual work.
- Proposed package layout (design proposal):
  - `manifest.json`: schema version, id/slug, title, artist, duration, sample rate, source-file hash, tool and model versions, detected key and BPM, lyric source, available baked key variants.
  - `instrumental.flac`, `vocals.flac` (optional `drums.flac`, `instrumental_k-4.flac`, ...).
  - `notes.auto.json`, `notes.json`, `lyrics.json`, `beats.json`, `f0.json` (10 ms hop pitch curve of the original vocal for display), `peaks.json` (waveform overview), optional `song.ultrastar.txt`.
- Stem sizes (arithmetic, 4-minute stereo 44.1 kHz): 16-bit WAV is 44100 × 2 × 2 × 240 ≈ 42 MB per stem; FLAC is typically 50–65% of that, about 21–28 MB; 256 kbps AAC/Opus about 7.7 MB; so a package with instrumental + vocals + one baked key variant is roughly 65–85 MB in FLAC or about 25 MB lossy. Decoded in the browser as Float32 at 48 kHz, each stereo stem is about 92 MB of RAM (240 × 48000 × 2 × 4 bytes), fine for a MacBook Pro with 2–3 stems loaded.
- Prefer FLAC (or WAV) over AAC/MP3 for stems: lossy codecs add encoder delay/padding that can offset decoded audio by tens of milliseconds and differ between decoders, which would silently skew note/lyric timing relative to audio (background, unverified; trivial to avoid by using FLAC, which browsers decode via `decodeAudioData`).
- Environment management: one `pyproject.toml` with `uv` and a pinned Python (3.12 satisfies audio-separator, mlx-audio-separator, GAME and UltraSinger), a lockfile, and optional dependency groups (`mlx`, `whisperx`, `game`) so a heavy or conflicting tool can instead be run in its own isolated environment via `uvx`/`uv tool run`. Conflicting torch pins between tools (audio-separator needs PyTorch 2.13+ on Apple Silicon; GAME was tested on 2.8.0) are the most likely install problem; isolating each stage as a subprocess with its own environment avoids it.
- Robustness practices: make each stage idempotent and cached by input hash (`separate`, `lyrics`, `align`, `notes`, `beats`, `render-key`), record tool/model versions in the manifest, and write to a temp folder then rename so the web app never sees a half-written package.

### Gaps
- OPFS quotas/eviction behaviour and Chrome's persistent-permission behaviour for stored directory handles were not verified this session.
- No source was found comparing these architectures for a karaoke/practice tool specifically; the recommendation is engineering judgement.

## 8. Overall recommended pipeline and fallback (synthesis)

### Takeaway
Recommended: a `uv`-managed local CLI that runs BS-RoFormer separation (`audio-separator`), LRCLIB-or-pasted lyrics with wav2vec2 forced alignment, SwiftF0 pitch with word-constrained note segmentation, `beat_this` beats, and writes a FLAC + JSON song package; the React app plays it through Signalsmith Stretch for live key/tempo and offers a small note editor. Fallback: run UltraSinger unmodified to get stems + UltraStar txt, import that txt, and pre-render key variants with the Rubber Band CLI.

### Cited Findings
- `audio-separator` 0.48.0 (MIT, 29 Oct 2026) with `model_bs_roformer_ep_317_sdr_12.9755.ckpt` lists vocals SDR 12.9 / instrumental 17.0 versus 10.8 vocals for `htdemucs_ft`. — [PyPI audio-separator](https://pypi.org/project/audio-separator/)
- `demucs-mlx` separates a 3:15 track in 2.7 s on an M4 Max (PyTorch MPS 6.9 s). — [PyPI demucs-mlx 1.1.0](https://pypi.org/project/demucs-mlx/1.1.0/)
- LRCLIB provides keyless line-synced lyrics with ±2 s duration matching and a `hasWordSync` flag. — [LRCLIB docs](https://lrclib.net/docs.md)
- WhisperX provides wav2vec2 forced alignment and runs on CPU on Mac; Nightingale uses LRCLIB first then WhisperX large-v3 on isolated vocals. — [m-bain/whisperX](https://github.com/m-bain/whisperX), [Nightingale docs: lyrics](https://nightingale-379.pages.dev/docs/lyrics)
- Whisper large-v3 on a separated vocal stem is about 22% WER on songs locally, and `condition_on_previous_text` must be off. — [lyrics-bench paper](https://lyrics-bench.onrender.com/papers/paper.html)
- UltraSinger (MIT) implements Demucs → Whisper → SwiftF0 → hyphenation → UltraStar txt/MIDI, is CPU-only on macOS and still labelled under development. — [rakuri255/UltraSinger](https://github.com/rakuri255/UltraSinger)
- Signalsmith Stretch is MIT with an official WASM/AudioWorklet npm build; best for 0.75x–1.5x time-stretch. — [Signalsmith-Audio/signalsmith-stretch](https://github.com/Signalsmith-Audio/signalsmith-stretch)
- Rubber Band v4.0.0 CLI (GPL) with `-3` R3 engine gives the better offline result at higher CPU cost. — [Rubber Band Library](https://breakfastquay.com/rubberband/), [Rubber Band CLI usage](https://breakfastquay.com/rubberband/usage.txt)
- `beat_this` is the current state-of-the-art beat/downbeat tracker and installs from GitHub without madmom. — [PyPI beat-this](https://pypi.org/project/beat-this/)

### Inferences
Recommended import pipeline (`songprep import <audio> --artist A --title T [--lyrics file] [--language en]`):
1. Decode/normalise with ffmpeg to 44.1 kHz stereo WAV; hash the source.
2. Separate: `audio-separator <wav> --model_filename model_bs_roformer_ep_317_sdr_12.9755.ckpt` → `vocals.flac`, `instrumental.flac`. Optional flags: `--fast` uses `demucs-mlx htdemucs`; `--mlx` uses `mlx-audio-separator`; `--lead-only` adds a karaoke-model pass to strip backing vocals for analysis.
3. Lyrics text: user file, else LRCLIB `/api/get` with duration, else mlx-whisper large-v3 on `vocals.flac` (`condition_on_previous_text=False`, explicit language) flagged "needs review".
4. Word timing: wav2vec2 forced alignment (WhisperX align module on CPU) per line window anchored on LRC line times; estimate and store a global lyric offset.
5. Notes: SwiftF0 f0 on the vocal stem → word-constrained segmentation with the vibrato/merge/octave heuristics in section 2 → `notes.auto.json` + `f0.json`. Optional experiment: GAME as an alternative segmenter.
6. Analysis: `beat_this` beats/downbeats; key estimate; phrases from lines + rests; range/tessitura; recommended shifts for the stored singer profile.
7. Package: write the folder atomically; later `songprep render-key <song> --semitones N` bakes a Rubber Band R3 key variant (optionally with unshifted drums).

Web app:
- Load packages as static files from the local server; decode stems to AudioBuffers; play through one Signalsmith Stretch node per stem group (or one node with summed buffers) using `addBuffers` + `schedule({ rate, semitones })`; phrase looping via `loopStart/loopEnd`; count-ins from `beats.json`.
- Note editor (piano roll over f0) writing `notes.json`; lyric-offset and tempo-halving controls; key picker driven by the tessitura cost function with an octave-down option.

Fallback pipeline (if the custom note/alignment stages prove too costly to build or tune):
- Run UltraSinger as a separate tool (`UltraSinger.py -i song.mp3 -o out --whisper large-v3 --language en --keep_cache`), accept CPU-only speed, and import its UltraStar txt (parsed by the in-house `ultrastar.ts`) plus the stems it produced; re-separate with `audio-separator` only if stem quality is inadequate; fix octaves/notes in the same editor. A user-found community UltraStar txt goes through the same import path (re-fit `#GAP`, re-anchor octaves against f0).
- Key/tempo fallback: pre-render the instrumental with `rubberband -3 -p <N>` at import and use SoundTouchJS (MPL-2.0) or native `playbackRate` for tempo if Signalsmith integration misbehaves.

Main risks to budget for in the spec:
- Note accuracy on real commercial vocals is unmeasured; the editor is not optional.
- Torch version conflicts between tools; isolate stages in separate environments.
- Lyric timing drift between LRCLIB/community data and the user's specific audio master.
- Pitch-shift artefacts at −5/−6 semitones; mitigated by the drums-unshifted pre-render and by considering "smaller shift + sing an octave lower".

### Gaps
- End-to-end import time on the user's MacBook Pro is unknown (expected to be dominated by BS-RoFormer separation and CPU forced alignment); measure on the first song.
- No head-to-head evidence that the custom f0 + word-boundary segmentation beats UltraSinger's output or GAME on the user's material; a one-afternoon bake-off on two songs should decide.
